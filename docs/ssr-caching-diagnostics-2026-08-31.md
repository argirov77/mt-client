# Диагностика SSR-рендеринга и кэширования — maximovtours.com

Дата: 31.08.2026. Тип: диагностика по ТЗ (аудит 46 страниц). Код не менялся, PR не открывался.

Среда выполнения: удалённая сессия Claude Code с клоном репозитория `argirov77/mt-client` (main, коммит `87b091e`).
**Важное ограничение среды:** сетевая политика сессии запрещает исходящие соединения к произвольным доменам.
Соединения к `maximovtours.com:443` и к бэкенду `38.79.154.248:80` отклоняются egress-прокси
(403 на CONNECT, отказ за ~6 мс — это прокси, а не сервер). Поэтому пункты блока A, требующие живого
браузера, помечены как невыполнимые из этой среды; для каждого дан прогноз из кода и методика ручной проверки.

---

## Блок A. Работает ли это для живых пользователей

**Статус блока: живая проверка из этой среды невозможна** (egress-политика блокирует и сайт, и бэкенд;
Chromium/Playwright в среде есть, но открыть страницу не через что). Ниже — что предсказывает код и что
проверить вручную.

### A1. Блок «Наши маршруты» после гидратации
Не выполнено (нет сетевого доступа). **Прогноз из кода: да, заполняется.** `Routes.tsx` — клиентский
компонент, в `useEffect` шлёт `POST /api/selected_route` с телом `{"lang":"<locale>"}`
(`src/components/Routes.tsx:92-96`). `/api/*` силой (`force = true`) проксируется Netlify-редиректом на
`http://38.79.154.248/api/:splat` (`netlify.toml:8-12`) — same-origin, CORS не нужен. Если бы этот
запрос падал у живых пользователей, форма бронирования (те же `/api/*`) тоже была бы мертва, а событие
`purchase` в GA4 не приходило бы — оно приходит.

### A2. Таблица «Актуальные тарифы» после гидратации
Не выполнено. **Прогноз: да, заполняется.** `Schedule.tsx` в `useEffect` шлёт
`POST /api/selected_pricelist` через axios-клиент (`src/components/Schedule.tsx:40`), тот же прокси-путь.

### A3. Запросы на бэкенд
Не выполнено из среды. Из кода известен полный список запросов публичных страниц:

| Запрос | Метод | Откуда | Файл |
|---|---|---|---|
| `/api/selected_route`, тело `{"lang":…}` | POST | блок «Наши маршруты», после монтирования | `src/components/Routes.tsx:92` |
| `/api/selected_pricelist`, тело `{"lang":…}` | POST | блок «Актуальные тарифы», после монтирования | `src/components/Schedule.tsx:40` |
| `/api/search/departures`, `/api/search/arrivals` | GET, `cache:'no-store'` | выпадающие списки формы | `src/components/hero/DirectionSelect.tsx:86,132` |

Статусы/тайминги/тела замерить вручную:
`curl -s -w '%{http_code} %{time_total}\n' -X POST https://maximovtours.com/api/selected_route -H 'Content-Type: application/json' -d '{"lang":"ru"}'`
(и то же для `selected_pricelist`).

### A4. Ошибки в консоли
Не выполнено. Из кода: CORS исключён (same-origin через прокси); mixed content исключён (браузер ходит на
HTTPS-домен, HTTP до `38.79.154.248` — серверная нога Netlify-прокси); оба компонента ловят ошибки и
рендерят текстовое состояние, а не бросают исключение (`Routes.tsx:108`, `Schedule.tsx:42-43`).

### A5. Время от первого байта до данных
Не выполнено. Структурная оценка из кода + данных аудита: TTFB (495–659 мс тёплый, 4400–5300 мс холодный)
**+** загрузка и парсинг JS-бандла **+** гидратация **+** RTT двух POST-запросов через прокси на бэкенд.
Данные физически не могут появиться раньше гидратации — в HTML их нет. На холодном заходе это
ориентировочно 6–8 с и хуже на A6-профиле.

### A6. Мобильный viewport + Slow 4G
Не выполнено (та же причина). Прогноз: те же два блока заполняются, но позже — на Slow 4G штраф
последовательности «HTML → JS → гидратация → XHR» максимален, «Маршруты не найдены»/«Загрузка…» видны
пользователю несколько секунд как FOUC-состояние.

## Блок B. Почему данных нет в серверном HTML

### B1. Где живут запросы
Оба запроса — **клиентские компоненты с `useEffect`**. Серверных запросов за маршрутами и ценами в проекте нет вообще.

- Маршруты: `src/components/Routes.tsx` — `"use client"` (строка 2), запрос в `useEffect` (строки 87–114),
  `fetch(`${API}/selected_route`, {method:"POST", …})`.
- Цены: `src/components/Schedule.tsx` — `'use client'` (строка 1), запрос в `useEffect` (строки 35–51),
  `apiClient.post('/selected_pricelist', { lang })`.
- Монтируются из серверных страниц: `src/app/[locale]/(site)/page.tsx:49-50` (главная) и
  `src/app/[locale]/(site)/[trip]/page.tsx:77-78` (12 посадочных), но пропсом передаётся только `lang` —
  данных сервер не передаёт.

### B2. Если запрос серверный — почему данные не в HTML
**Не применимо: запрос не серверный.** При SSR он не выполняется вовсе — `useEffect` на сервере не
запускается. Ничего не падает и ничего не глотается: сервер честно рендерит начальное состояние стейта.
Попутный факт: даже если этот код вызвать на сервере, он упадёт — в проде `API_BASE = "/api"`
(относительный URL, `src/lib/apiBase.ts:7`), а серверный `fetch` в Node требует абсолютный URL.

### B3. Достижим ли бэкенд из Netlify-функции
Netlify-функция бэкенд **не вызывает вовсе** (см. B1), поэтому её достижимость на текущие дефекты не влияет.
Факты для будущего серверного фетча:

- Адрес: `http://38.79.154.248`, порт 80, **plain HTTP** (netlify.toml:10). Из Netlify-функции придётся
  ходить на этот адрес напрямую (относительный `/api` в функции не работает) — если у бэкенда есть
  IP-allowlist на адреса Netlify, это надо проверить у бэкенда; из данного окружения проверить нельзя (egress закрыт).
- Авторизация: для `selected_route` фронт не шлёт ни cookie-зависимых заголовков, ни CSRF (голый `fetch`);
  `apiClient` добавляет `X-CSRF` из cookie `mc_csrf` только для не-GET (`src/lib/apiClient.ts:9-29`), и
  `selected_pricelist` при первом заходе уходит без него и, судя по работе прода, принимается. То есть
  публичные эндпоинты анонимные.
- Гипотеза «переменная окружения задана локально, но не в Netlify» — **не подтверждается**:
  `NEXT_PUBLIC_API_BASE` / `NEXT_PUBLIC_API_URL` / `REACT_APP_API_URL` читаются только в dev-ветке;
  в production база захардкожена в `"/api"` (`src/lib/apiBase.ts:1-9`). От env-переменных прод не зависит.

### B4. Тайминги бэкенда (p50/p95)
Не выполнимо из этой среды (сеть закрыта). Методика: 20× `curl -w '%{time_total}'` на оба эндпоинта через
`https://maximovtours.com/api/...` и, при доступе, напрямую на `38.79.154.248`, чтобы отделить долю прокси.
Важно: текущие TTFB страниц (495–659 мс) бэкенд-таймингов **не содержат** — SSR к бэкенду не обращается.

### B5. Почему «Маршруты не найдены», а не скелетон
Решение принимается начальным значением стейта `loading`:

- `Routes.tsx:81` — `const [loading, setLoading] = useState(false);` ← **false**. `setLoading(true)`
  вызывается только внутри `useEffect` (строка 89), которого при SSR нет. На сервере: `loading=false`,
  `err=null`, `forward/backward=null` → ветка `Routes.tsx:130`
  `{!loading && !err && !hasAny && <p className={styles.empty}>{L.noData}</p>}` → «Маршруты не найдены» (`noData` в `src/translations/home.ts:179`; локализованные варианты — строки 198, 212, 226).
  Скелетон (`SkeletonCards`, строка 126) показывается только при `loading===true`, т.е. никогда в SSR-HTML.
- `Schedule.tsx:31` — `const [loading, setLoading] = useState(true);` ← **true**, поэтому там SSR-HTML содержит
  «Загрузка…» (`Schedule.tsx:76-78`, строка из `src/translations/home.ts:129`). Два компонента написаны с противоположными начальными состояниями —
  отсюда разные плейсхолдеры у двух блоков.

Для SEO вариант Routes хуже: «Маршруты не найдены» — это семантически «данных нет», а не «данные грузятся».

## Блок C. Почему отключён кэш

### C1. Middleware
Есть, но называется по конвенции Next 16: **`src/proxy.ts`** (в Next 16 `middleware.ts` переименован в
`proxy.ts` — потому Glob по `middleware.*` его не находит). Matcher (`src/proxy.ts:29-33`):
`/((?!_next/static|_next/image|_next/data|api|favicon.ico|robots.txt|sitemap.xml|icons/|images/|.*\..*).*)` —
**ловит все страницы**. Логика: для `/ua|/en|/bg` проставляет request-заголовок `x-locale`, для остальных
путей делает rewrite `/x` → `/ru/x` и тоже ставит `x-locale`. Сам по себе proxy кэш не снимает и
`cache-control` не трогает, но он — источник заголовка, который читается в C2. Подозреваемый №1 из ТЗ
подтверждается наполовину: локаль действительно определяется через middleware, но убийца кэша — не matcher,
а чтение `headers()` ниже.

### C2. Динамические функции — ★ первопричина дефекта №1
**Подтверждено.** `src/app/layout.tsx:31` — корневой layout:
```ts
const headerStore = await headers();
const headerLocale = headerStore.get("x-locale");
```
Одно это обращение переводит **всё дерево всех маршрутов** в dynamic rendering. Именно поэтому
`generateStaticParams` на `[locale]/layout.tsx:6` и `[trip]/page.tsx:23` не даёт статики: прекомпилировать
нечего, каждый запрос рендерится функцией. Next для динамического ответа ставит
`cache-control: private, no-cache, no-store, max-age=0, must-revalidate`, Netlify честно отвечает
`cache-status: "Netlify Durable"; fwd=bypass` — durable cache обходится, потому что ответ помечен
некэшируемым. Отсюда же холодный TTFB 4400–5300 мс: каждый первый запрос будит серверлес-функцию
(cold start), статикой/кэшем он бы не существовал. Других обращений к `cookies()/headers()/draftMode()`
в серверном коде нет (проверено grep'ом по `src/`); `useSearchParams` есть только в клиентских компонентах.

### C3. Явные директивы
Ни одного вхождения `export const dynamic`, `export const revalidate`, `export const fetchCache`,
`force-dynamic` в репозитории нет. Не применимо.

### C4. Опции fetch
Все обращения к бэкенду — клиентские, на серверный рендер их опции не влияют. Вхождения `no-store` (все —
клиентский код): `src/app/[locale]/(site)/return/page.tsx:424,876,917,934` (страница `"use client"`),
`src/components/SeatClient.tsx:79`, `src/components/hero/DirectionSelect.tsx:86,132`. Серверных fetch'ей
с опциями кэша нет вовсе. Не применимо к дефекту №1.

### C5. Заголовки вручную
Нигде не задаются: `next.config.ts` пуст (нет `headers()`), в `netlify.toml` секции `[[headers]]` нет,
файла `public/_headers` нет, `src/proxy.ts` заголовков ответа не ставит. `cache-control: private,…` —
это дефолт Next для динамического рендера, а не чья-то ручная настройка.

### C6. Версии и конфиги
- `next` **16.1.6** (package.json `^16.1.6`, package-lock — 16.1.6), `react` 19.2.4.
  Попутно: `eslint-config-next` 15.4.6 — отстаёт на мажор, на рантайм не влияет.
- `@netlify/plugin-nextjs` подключён в `netlify.toml` **без пина версии** и в package.json отсутствует —
  Netlify подставляет свой текущий v5-рантайм на каждом билде. Точную версию видно только в логе деплоя.
- Режим сборки: обычный `next build`, `publish = ".next"`, без `output: 'export'` и без standalone.

## Блок D. Что можно вынести в статику

### D1. Список маршрутов
С бэкенда приходить **не обязан**. Более того, репозиторий уже содержит статический справочник
`src/lib/tripsData.ts` (905 строк): 12 направлений + хаб `route`, слоги на 4 локалях, реальные `stop.id`
(`STOP = { odessa: 4, bolgrad: 5, constanta: 7, varna: 10, sunnyBeach: 14, burgas: 15 }`), тексты. Бэкенд
(`/selected_route`) добавляет к этому только: локализованные названия/описания остановок, времена
прибытия/отправления и ссылки на карту. Потеряем при хардкоде: правка времён и остановок в админке будет
требовать деплоя. Компромисс (рекомендуемый): не хардкодить, а фетчить **на сервере** с
`next: { revalidate: 3600 }` — данные попадают в HTML, деплой для правок не нужен, устаревание ≤ 1 ч.

### D2. Цены
В ответе `/selected_pricelist` клиентский код видит только `{ prices: [...] }` — признаков актуальности
(timestamp/ETag) фронт не читает; есть ли они в заголовках ответа — из этой среды проверить нельзя,
посмотреть в DevTools при ручной проверке A3. Кэшировать на N минут — да, штатно: серверный fetch с
`next: { revalidate: 300–900 }`. Фолбэк «последняя известная цена» при ISR получается бесплатно: при
недоступном бэкенде на ревалидации Next продолжает отдавать последний успешно собранный HTML, «Загрузка…»
из серверного HTML исчезает как класс. Частоту реальных изменений цен ответить может только владелец
бизнеса/бэкенда — в коде ответа нет.

### D3. Что обязано остаться динамическим
Строго говоря, **персональные/транзакционные страницы**, и все они уже `noindex`:

| Маршрут | Почему динамический |
|---|---|
| `/booking` | наличие мест, выбор рейса/кресла — живые данные (по ограничению ТЗ) |
| `/cabinet` | личный кабинет, сессия пользователя |
| `/purchase/[purchaseId]` | статус конкретной покупки |
| `/ticket/[id]` | конкретный билет |
| `/q/[opaque]` | QR-обмен билета |
| `/return` | сценарий возврата: `no-store`-запросы статусов покупки |
| `/api/*` | прокси на бэкенд, не кэшируется по определению |

Нюанс: у всех них данные и так грузятся клиентски (`PurchaseClient`, `BookingCard` — client components),
так что их «динамичность» — это динамичность XHR, а не HTML; но по ограничению ТЗ считаем их динамическими.
Блоки наличия мест внутри публичных страниц (`BookingSection` на главной и посадочных) остаются клиентскими
XHR и статике страницы не мешают.

### D4. Что мешает SSG 52 публичных страниц и объём работ
Мешают ровно две вещи, обе локальные:

1. **`headers()` в корневом layout** (`src/app/layout.tsx:31`) — читает `x-locale` ради `<html lang>`.
   Убрать: перенести `<html>/<body>` в `src/app/[locale]/layout.tsx` (сделать его корневым layout'ом —
   штатный i18n-паттерн Next), брать локаль из `params`, у которых уже есть `generateStaticParams`.
   `src/proxy.ts` остаётся как есть: rewrite `/odessa-varna` → `/ru/odessa-varna` умеет отдавать
   прекомпилированную страницу.
2. **Клиентский фетч маршрутов/цен** — чтобы статика была содержательной, а не статикой заглушек:
   перенести запросы `selected_route`/`selected_pricelist` в серверные компоненты с `revalidate`
   (адрес бэкенда — env-переменная в Netlify, т.к. серверу нужен абсолютный URL), данные передавать в
   `Routes`/`Schedule` пропсами; интерактив (раскрытие остановок) остаётся клиентским.

Инфраструктурных препятствий нет: `generateStaticParams` уже написан для обеих осей (локали и трипы),
`@netlify/plugin-nextjs` v5 поддерживает ISR/Durable Cache из коробки, ручных `cache-control` нет.
Оценка — в «Выводе».

## Вывод

**Первопричины трёх дефектов (их две, а не три):**

1. **CDN не кэширует** — `await headers()` в корневом `src/app/layout.tsx:31` (читает `x-locale`,
   проставленный `src/proxy.ts`) переводит все 100 % маршрутов в динамический рендеринг; Next помечает
   каждый ответ `private, no-store`, Netlify Durable Cache обходится (`fwd=bypass`), холодный TTFB
   4,4–5,3 с — это cold start серверлес-функции на каждый непрогретый запрос.
2. **«Наши маршруты» пуст в SSR** и 3. **«Актуальные тарифы» = "Загрузка…"** — общая причина: данные
   запрашиваются только в браузере (`useEffect` в клиентских `Routes.tsx` и `Schedule.tsx`); серверного
   запроса к бэкенду не существует ни на одной странице, поэтому в HTML/RSC-payload данных нет и быть
   не может. Разница плейсхолдеров — лишь начальное значение `loading`: `false` в Routes (→ «не найдены»)
   против `true` в Schedule (→ «Загрузка…»). Гипотеза «бэкенд недоступен из Netlify / env не задан» не
   подтвердилась: прод не зависит от env-переменных, а Netlify-функция к бэкенду вообще не обращается.

**План правок (согласуется отдельно, оценки в часах):**

| # | Работа | Часы |
|---|---|---|
| 1 | Убрать `headers()`: перенести `<html>/<body>` и `lang` в `[locale]/layout.tsx`, локаль из `params`; проверить `proxy.ts`-rewrite на статике | 3–5 |
